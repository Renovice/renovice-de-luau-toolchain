# Warframe native API contracts

This folder is the authoritative contract registry for writing intentional
Warframe Lua/Luau edits. It is deliberately separate from
`cert/warframe_api`: the certification mock tests compiler/decompiler behavior,
while this registry records what the real game API is actually known to do.

## Confidence model

- `LIVE_CONFIRMED`: observed in the real private-server game environment.
- `STOCK_BYTECODE`: directly present in shipped DE bytecode or inspected native
  bindings, but not necessarily live-probed for every return type or lifetime.
- `OFFLINE_FIXTURE`: useful translator evidence only. It must never be promoted
  into a real API contract without stock/native/live evidence.
- `UNRESOLVED`: explicitly unknown. Callers must preserve the uncertainty.

`contracts.tsv` is the machine-readable source of truth. It records visible
argument counts (method receivers are excluded), parameter and return types,
nested callback signatures, authority, lifetime, confidence, evidence IDs, and
limitations. `evidence.tsv` resolves those evidence IDs. Negative results are
first-class contracts in `negative_contracts.tsv`; they prevent a disproven
assumption from quietly returning in a later edit.

## Curated working set

`selection_seeds.tsv` defines exactly 225 unique `CORE` APIs chosen for ability
authoring. Exactly 175 of those also carry `HIGH_CONFIDENCE`; this is an
overlapping tier, not another 175 duplicate APIs. The high-confidence gate
requires either a detailed contract or one stable observed argument shape from
the audited 55,709-site bytecode census. APIs with observed overloads/open call
shapes remain useful `CORE` entries but cannot enter that stricter tier. The
2026-09-08 ability-focused expansion used the verified 248-entry/246-module
behavior catalog to prioritize 25 additional identities, while the original
55,709-site census remains the structural support authority.

`selected_catalog.tsv` is generated by `tools/warframe_api/wf_api_catalog.cpp`.
For every selection it records its bytecode hash, call sites, modules,
prototypes, observed encoded and source-visible argument widths, result widths,
consumption categories, and evidence grade. Regenerate it with
`tools\warframe_api\build_catalog.bat`. The build is gated on exactly 55,709
census rows, 225 supported core identities, and 175 high-confidence identities.

The catalog deliberately separates two levels of knowledge:

- `DEEP_CONTRACT` means the API also has a detailed row in `contracts.tsv`.
- `OBSERVED_STABLE_SHAPE` or `OBSERVED_STABLE_ARGS` means the call structure is
  stable across the corpus, but owner class, lifetime, exact native type, and
  overload semantics may still need stock/native/live evidence.

Consequently, return-family values in the broad catalog are authoring hints,
not substitutes for the typed/lifetime claims in `contracts.tsv`.

## Lightweight intentional-script workflow

For a new or modified ability script:

1. Run `check_ability_api.bat <source.luau>`. This performs a normal DE
   compilation to the Windows `NUL` device and a fast contract check. It does
   not scan or rebuild the 286-module corpus.
2. Resolve every contract violation. Review unverified method names that belong
   to the intentional edit; stock calls outside the edited area may remain
   unregistered while the registry is still growing.
3. Compile the actual replacement once the focused check is clean.
4. Test the behavior in game and inspect `EE.log`.
5. If the live result establishes a new signature/type/lifetime fact, add one
   evidence row and update the contract. If it disproves an assumption, add a
   negative contract as well.

For a full native replacement, pass the verified stock source as a baseline:

```text
check_ability_api.bat replacement.luau --baseline verified-stock.luau --strict-unknown
```

The checker subtracts the stock multiset of method/global name, visible
argument count, and callback arity before applying strict checking. This keeps
untouched stock APIs outside the current catalog from blocking a replacement,
while a call shape introduced by the edit must still be registered. The
baseline path is recorded and hash-pinned by Ability Studio staging. Because
receiver types are not inferred, the subtraction does not prove that two calls
with the same shape use the same native receiver type; instruction-addressed
semantic proof and replacement plan verification remain separate gates.

Run corpus-wide certification only when the decompiler, renderer, compiler,
normalizer, or shared API mock infrastructure changes. An ordinary intentional
ability edit does not need the full R&D corpus gate.

The checker is deliberately honest about its current boundary. Detailed
contracts validate method/global names, visible argument counts, and nested
callback arity. The broad catalog additionally validates the 175 stable/deep
high-confidence call shapes and identifies the other 50 overload-dependent core
calls as known. It does not yet infer the concrete type of every receiver, and
field contracts are recorded but not statically type-checked. Unknown calls are
non-fatal by default because a reconstructed stock module contains many APIs
that have not yet entered this registry. Use `--show-unknown` to list them, or
`--strict-unknown` for a small fully authored add-on that should use only
registered calls.

The first 2026-09-08 expansion added 50 named action methods only where every audited
stock callsite has one exact encoded argument width and zero results. Catalog
owners are recorded as `UnresolvedReceiver` until receiver evidence exists;
parameter names and meanings remain unresolved. `HIGH_CONFIDENCE` therefore
certifies the observed method name, hash, visible arity, and zero-result shape,
not an invented receiver class or gameplay-side semantic contract.

The second 2026-09-08 expansion added 25 ability-authoring queries and controls.
Every added identity has exactly one method hash, one encoded argument width,
and one result width in the same pinned census. The synchronized ability map
then promoted eight receiver/signature contracts where exact value flow was
consistent. Those stock contracts do not claim live gameplay timing or
multiplayer replication.

## Current first slice

The first live-confirmed slice covers the working Octavia Mallet edit:

- `Engine.RadialDamageData()` construction and stock packet configuration;
- `RadialDamageData:SetDamageCallback(function(damagedTarget: AvatarOrEntity, damageAmount: number))`;
- `gRegion:RadialDamage(packet)` owning victim/radius selection;
- caster `DamageControl` Overguard reads/writes;
- `GetPlayer()` composed into `NotifyOverguardGain(player, positiveDelta)`;
- authority and lifetime facts that remain unresolved.

The important negative contract is permanent: callback argument 2 is numeric,
not a DamageData object. V51 live identity evidence establishes callback
argument 1 as a callback-local reference whose underlying object is the
damaged `AvatarOrEntity`; callers must not retain it after the callback. V52
proved that this wrapper does not expose `IsDead`, so native object identity
must not be confused with a complete ordinary Avatar Lua method table.

## Runtime value and transaction rules from Ice Wave

The 2026-09-14 Ice Wave investigation added five permanent authoring rules:

1. `DamageData:GetBaseAmount()` returned an engine-owned `UpgradedValue`
   wrapper whose numeric reading changed when the owning packet changed. It was
   a live view at that callsite, not an immutable snapshot. Copy
   `GetModifiedValue()` into a Lua number before mutation when restoration is
   required.
2. Repeated userdata equality or a repeated printed native address does not
   prove logical transaction identity. The native allocator reused one address
   for consecutive logical packets created inside the stock target loop.
3. A target-local calculation must explicitly install its value for every
   target, including the 1x case. Skipping the setter can retain another
   target's modified packet value.
4. Hook coverage is layer-specific. The exact native `DamageDD` hook ran while
   the expected nested `luaCalls[7].before` callback did not. Select a hook from
   observed execution, not from a matching prototype label alone.
5. Ordinary Luau library contents are not guaranteed in DE's VM. The tested
   target environment exposed `math.min` but not `math.huge`.

These rules describe runtime behavior and addon authoring. They do not change
the meaning of an opcode, DE-container roundtrip, compiler fixed point, or
Semantic IR verification. A bytecode-perfect program can still contain an
incorrect assumption about native userdata lifetime.
