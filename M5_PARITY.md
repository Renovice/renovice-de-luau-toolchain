## Why the original M5 spec was abandoned

`ARCHITECTURE.md` originally specified *"recompile the corpus subset; match Python's 99.98% round-trip."*
**That metric is invalid**, and chasing it would have produced a meaningless number.

`all_source_v13/v14/v15` were generated by the **old Python decompiler using the opcode map we have since
proven wrong** — it had `MUL=0x09`, `JUMPIFLT`/`JUMPIFLE` swapped, `NAMECALL=0x36` (an opcode that occurs
**zero** times in the entire corpus), `0x17` misread as a field read, and `PREPVARARGS` dropped entirely.

So the old "99.98% faithful" figure measured **self-consistency of a flawed pipeline**: decompile with a
wrong map, recompile with the same wrong map, and of course it round-trips. It would score 99.98% even if
every `<=` in the game were silently a `<`.

**Concrete proof of contamination.** `all_source_v13/EE_Interface_AnchorMgr.lua.lua:22` renders:
```lua
elseif v2 == unk5.ANCHOR_H_RIGHT or (v2 == unk5.ANCHOR_H_CENTRE or v2 ~= unk5["function"]) then
```
— a field read on a table `unk5` that does not exist. The bytecode is `0x17`, which is **GETGLOBAL**: these
are bare globals (`ANCHOR_H_RIGHT`), not fields of anything.

**Consequence:** v13/v14/v15 must be **regenerated** by M6, not repaired. They are outputs of the broken map.

## The metrics that replaced it

All three use **only** shipped `.lua_B` bytecode and our own code. No decompiled source anywhere in the
loop, so no circularity.

### 1. Container round-trip
Parses the DE container, **structurally rebuilds** the constant table from parsed form (not copied), and
re-emits. Header/code/post are preserved as raw spans. `5382/5382` byte-exact.

### 2. Decode validation (`de-validate`)
For every instruction, checks the operands our decode map *implies* are actually in range:
* register operands `< maxstack`
* constant indices `< nconsts`
* branch targets in range **and** on an instruction boundary
* the width table walks each proto to **exactly** its code end

A wrong decode shows up as an impossible operand. Result: **0 violations across 5,529,086 instructions**,
82042/82042 clean walks.

> It also settled a live question as a side effect: `0x0b` was marked a branch as a *hypothesis*, and all
> 1219 of its targets land on instruction boundaries — which they would not if it were not one. This
> corroborates the FORGPREP-family reading.

> And it caught two of the author's own bugs within three runs: an over-strict `RETURN` check (`A` is only
> a live register when `B>1`), and a `//` comment inserted mid-line that silently disabled the `GETUPVAL`
> table entry — surfaced immediately as "`0x13` unknown ×351,302".

### 3. Instruction round-trip (`de-recode`) — the strongest test
The container round-trip never actually decodes an instruction; `code` is an opaque raw span. This one
fully decodes every instruction, stores each branch as a **target instruction index**, then rebuilds the
byte stream **recomputing every offset from that index**. The original `Bx` of every branch is discarded.

Therefore:
* a wrong **width** → different layout → different bytes
* a wrong **jump base** (`op+4`) → different offsets → different bytes
* a **misclassified branch** → offset packed into B/C instead → different bytes

**82042/82042 = 100.0000% byte-identical.** The instruction model is lossless on all real bytecode.

## What this does and does not prove

**Proves:** our *structural* decode — opcode set, widths, operand layout, branch encoding — is complete and
lossless across every shipped script. This is the foundation M6 stands on.

**Does not prove:** the *semantic* meaning of each opcode. A consistent-but-wrong reading of an op's meaning
would still round-trip. Semantics were established separately, by in-game substitution probes
(`METHODOLOGY.md`) and the 10-module cert suite.

**Does not prove:** that we can produce readable, recompilable **source**. That is M6, and the honest number
there is currently unknown — the ~21% figure quoted earlier was measured against the contaminated v13 and
should be discarded.

## Status

M5 complete. M1–M5 done. Next: **M6** — the C++ decompiler, which now has:
* a decode map covering **77/77** corpus opcodes,
* a **lossless** instruction model (this document),
* a validator (`de-validate`) that will catch regressions,
* and a clear first deliverable: **regenerate the corpus** to replace the contaminated v13/v14/v15.

Suggested M6 oracle: **round-trip idempotence** (decompile → recompile → decompile, require
source₁ == source₂) rather than byte-identity, which is unreachable because DE emits instrumentation
(`0x19`/`0x25`) and makes its own register-allocation and inline-cache-slot choices.
